# 压力测试报告解读指南：哪些指标才真正重要

## 概述

跑完一次压力测试后，你拿到一份报告——PPS多少、Gbps多少、并发连接数多少。但这些数字到底意味着什么？哪些指标能说明防护是否真的扛住了？本文拆解压力测试报告中的核心指标，帮你做出准确判断。

## 核心指标详解

### 1. 吞吐量

- **Gbps（千兆比特/秒）**：衡量带宽压力大小
- **含义**：目标服务器在带宽层面承受的总流量
- **误读**：高Gbps不等于有效攻击。如果90%是UDP垃圾包，被防火墙直接丢弃，服务器实际无感
- **正确理解**：关注有效到达服务器的Gbps，而非总输出

### 2. 包速率

- **PPS（Packets Per Second）**：每秒数据包数量
- **含义**：比Gbps更重要的指标。CPU处理每个包都需要中断，高PPS直接消耗服务器CPU
- **关键阈值**：普通服务器处理5万-10万PPS时CPU开始吃紧，20万+PPS会导致软中断占满CPU
- **误读**：很多人只看Gbps不看PPS，但1Gbps大包（MTU 1500）只有约8万PPS，1Gbps小包（64字节）高达190万PPS——后者杀伤力远超前者

### 3. 并发连接数

- **Concurrent Connections**：同时建立的连接数
- **含义**：L7测试的核心指标，反映服务器维持连接的能力
- **关键阈值**：取决于服务器配置。Nginx默认worker_connections=1024，超过后新连接被拒绝
- **误读**：连接数高不等于压垮了服务器。如果连接都处于ESTABLISHED但空闲状态，资源占用有限

### 4. 请求速率

- **RPS（Requests Per Second）**：每秒HTTP请求数
- **含义**：L7应用层压力的直接衡量
- **关键点**：区分"建立的连接"和"实际处理的请求"。服务器可能接受连接但处理请求很慢——后者才是真正的瓶颈
- **误读**：高RPS如果都是静态资源请求，CDN直接缓存返回，不触及源站

### 5. 响应延迟变化

- **TTFB（Time To First Byte）**：首字节响应时间
- **含义**：最能反映服务器真实压力的指标。TTFB从100ms飙升到5000ms说明服务器CPU/内存资源耗尽
- **关键阈值**：正常TTFB < 500ms，受压时 > 2000ms表示服务器接近极限
- **误读**：不记录TTFB变化的报告等于没测。只有最终"成功/失败"状态不够

## 常见误读与陷阱

### 陷阱1：只看总流量不看有效流量

很多压力测试报告标称"输出10Gbps"，但如果目标服务器有5Gbps带宽，超过的部分全部被网卡丢弃。有效压力只有5Gbps，报告的10Gbps没有实际意义。

**正确做法**：关注服务器带宽上限，超过上限的流量是无用功。

### 陷阱2：忽视CPU利用率

服务器被DDoS压垮，往往不是因为带宽不够，而是CPU被中断处理占满。

**正确做法**：压力测试时监控服务器CPU使用率、软中断比例。CPU到100%时，即使带宽还有余量，服务器也无法正常响应。

### 陷阱3：单一方法测试

只用一种方法测试就下结论："SYN flood打了5Gbps服务器没事，所以防护没问题。"

**正确做法**：多方法组合测试。L4打带宽 + L7打应用层，同时测试才能模拟真实攻击场景。

### 陷阱4：短时间测试

很多免费工具只跑30-60秒。部分防护机制（如CDN的自动扩容）需要时间生效，短测试可能给出误导性结论。

**正确做法**：至少持续3-5分钟的持续压力测试，观察防护系统的动态响应能力。

## 测试报告评估清单

一份有效的压力测试报告应包含：

- [ ] 总输出Gbps + 有效到达Gbps
- [ ] PPS（包速率）
- [ ] 并发连接数变化曲线
- [ ] 服务器CPU/内存利用率变化
- [ ] TTFB延迟变化曲线
- [ ] 测试方法清单（L4/L7各用了哪些）
- [ ] 测试持续时间（建议>3分钟）
- [ ] 防护系统的响应行为（限速触发、清洗启动等）

## 总结

压力测试报告的价值不在于"打了多大流量"，而在于"服务器在压力下的真实表现"。关注PPS而非仅看Gbps、监控CPU而非仅看带宽、记录TTFB变化而非仅看最终状态——这些才是判断防护有效性的核心指标。学会读报告，才能做出"防护是否真正有效"的准确判断。
